The notebook is the interface.

Code, figures and prose already live in one document. Nebula makes that document a real interface for both of you — you edit it, and your agent reads, edits and runs the same cells, in the same file, while you watch.

$npx nebula-notebook
then open localhost:3000

Built for the agent you already run

A CLI it already knows. Or MCP.

Nebula ships a real command-line interface and an MCP server. Whichever assistant you use drives the notebook through one of them — reading cells, editing them, running them and reading the output back, without a browser anywhere in the loop.

  1. It works on the file you're looking at

    nebula context reports the notebook you're viewing, and any operation on a different one carries a one-time notice — so "this cell" means what you think it means, even with two tabs open.

  2. Your edits are never clobbered

    Per-cell optimistic concurrency: if you've changed a cell since the agent read it, it gets your version back and re-applies its change on top, instead of overwriting you.

  3. It holds a visible session

    An agent takes the edit lock explicitly and the browser shows a badge while it's working, so nothing happens to your notebook invisibly.

And still a real notebook

Fast, honest, and yours to keep.

Everything above is useless if the notebook itself isn't good. Nebula is a complete notebook first — one you'd want even with no agent anywhere near it.

Kernels

Real Jupyter kernels

Python, R, Julia and anything else with a kernelspec, over ZeroMQ. Conda, venv, uv and pixi environments are detected for you; kernels survive a server restart and reattach.

Formats

Diffs you can review

First-class .ipynb, Quarto .qmd and percent-format .py. Outputs are never serialised into the text formats, so a one-line change is a one-line diff.

Speed

Big notebooks open instantly

Virtualised cells with progressive rendering; editors mount lazily and heights are pinned through the swap, so scrolling a thousand-cell notebook never jumps.

History

Undo that outlives the tab

Every structural edit — yours and the agent's — is journaled to disk. The history panel time-travels to any past moment with diff highlighting and restores it in one click.

Outputs

Interactive, not screenshots

Plotly and native JS outputs stay interactive, tqdm renders as one clean bar, and tall output or long source folds to a height you drag.

Access

Yours only

TOTP two-factor and passkeys, 30-day device sessions, and real tokens for agents — so a notebook on a shared login node stays yours.

Where your compute lives

Queue a node from the kernel menu.

On an HPC login node Nebula detects the scheduler and offers allocations directly: pick a partition and QoS from a live queue-load view — idle CPUs, idle GPUs by model, backlog — and your kernel comes up on the compute node. No sbatch script, no second SSH tunnel, nothing to hunt for.

It is detection-gated, so on a laptop you never see it. Heterogeneous clusters are handled too: queues are labelled by CPU architecture, and an ARM queue without a runtime hands you a setup brief filled with your own paths.

When the result matters

A figure you can prove.

Seal a result and Nebula re-runs the notebook top to bottom in a fresh, dedicated kernel, checks every output against the exploratory run, and binds the notebook, its artifacts and the environment into one hash-verified manifest. The sealed copy is read-only — the UI refuses edits, and so does the filesystem layer underneath.

It is the difference between a figure you believe and one you can hand to a reviewer.

Two commands.

Runs on your laptop, your lab server, or a cluster login node.

$npx nebula-notebook
$npx nebula-notebook-mcp setup-mcp
